§ 01 Approach

Two ideas hold the whole architecture up

The pipeline is a batch flow — ingest → transcribe → normalize → publish. It's value is that these two boundaries make the engine swappable.

Principle 01

Engine independence via CallRecord

The Normalize stage is the boundary. Nothing Deepgram-shaped crosses it — downstream only ever sees our vendor-neutral record -> minimal disruption.

Principle 02

Destinations behind one Sink

CRM and analytics implement the same interface, activated by config. Adding a destination or traffic-splitting the migration never requires a change inside the pipeline stages.

Your requirementWhere it's met
Minimal disruption to existing workflowsNormalize (CallRecord) + Publish (swappable sinks)
Custom support for industry-specific terminologyTranscribe — keyterm prompting (custom-trained model only if needed later)
Gradual migration path with parallel systems during transitionSink / feature-flag layer + shadow-run
Validation methodology to confirm accuracy improvementsWER + Keyword Recall Rate (KRR) vs. a ground-truth eval set
Integration with existing CRM & analyticsPublish (Sinks)

§ 03 Architecture decisions

Architecture decisions

DecisionWhy
Plain Node + TypeScript, no framework or build stepThe value is the pipeline, not the UI — fewer moving parts, readable end to end.
Official @deepgram/sdk, one thin wrapperNever hand-rolled REST/WebSocket; every option in one file, pinned to the installed version.
Batch, not streamingThe calls are already recorded — a throughput job. Streaming wouldn't fit the requirements.
Engine-independent CallRecord at the Normalize boundaryDownstream never sees Deepgram's response shape, so the engine is swappable.
Destinations behind a Sink interface + feature flagAdd, remove or traffic-split a destination by config — never by editing a stage.

§ 04 Metrics

How we measure accuracy and what each number means

Two metrics, side by side: WER for overall transcription accuracy, and Keyword Recall Rate for the terms that actually matter on a support call.

WER = ( S + I + D ) / N

Substitutions + Insertions + Deletions, over N = words in the ground-truth transcript — all three weighted equally.

KRR = keyterms recognized / keyterms spoken

Of the domain terms actually in the call, the fraction transcribed correctly. Keyword Error Rate (KER) is simply its inverse, 1 − KRR.

Reference   cancel my Genesys subscription this month
Engine      cancel my genesis subscription next month

WER = (2 subs + 0 ins + 0 del) / 6 words  = 33%
KRR = 0 of 1 keyterms correct             =  0%

Same sentence, two views: WER counts two wrong words out of six (33%), but KRR shows the one word that actually mattered — the platform name — was missed entirely. That gap is why both numbers ship together.

Normalize before you compare

Capitalization, punctuation, filler words and number formatting are normalized the same way across both engines first — otherwise you penalize style, not recognition.

Report the distribution, not a mean

Box plots (min / Q1 / median / Q3 / max) keep the 2% of bad-line-quality calls from hiding inside a flattering average.

And remember: WER against ground truth is accuracy; a WER diff without ground truth is only disagreement.

§ 05 Timeline

Five phases to cutover

The whole rollout is gated on metrics agreed up front. Deepgram runs on real traffic in shadow long before a single customer sees its output.

PHASE 0 · WEEK 1

Discovery & Baseline

System access, audio format & volume, build the eval set from your own recordings (min. ~1 h / ~10k words per condition), capture the current vendor's WER, agree acceptance thresholds.

No impact
PHASE 1 · WEEKS 2–3

Integration Build

Adapter to real CRM/analytics, tune the keyterm list, cloud-vs-self-hosted and data-residency decisions.

No impact
PHASE 2 · WEEKS 4–6

Shadow / Parallel

Deepgram runs on 100% of calls in shadow — output discarded. Daily WER + KRR vs. thresholds. A bad result costs nothing.

No impact
PHASE 3 · WEEKS 7–8

Gradual Cutover

Traffic ramps 5% → 25% → 50% → 100% via feature flag. Each step gated on the prior step's metrics. Rollback = flip the flag.

PHASE 4 · WEEK 9

Fully Operational

Current vendor switched off. Runbook + training handed over. Validation becomes standing operations, not a project artifact.

§ 06 For the support floor

What changes for your agents

This is post-call batch processing, not a new tool on the desk. The disruption budget is spent on engineering, not on the people taking calls.

  • The live call flow doesn't change. Transcription runs after the call ends — no new step or screen for agents.
  • Same CRM records, new engine. The CallRecord fields are identical; redacted PII appears exactly where it does now.
  • Invisible during the ramp. Some calls are Deepgram, some the current vendor — no one downstream can tell.
  • A handover, not a retrain. Phase 4 is a short brief for supervisors plus a runbook, not agent retraining.

§ 09 How we guide you

Your team owns this by the end — here's how we get you there

  1. Anchor everything on Phase 0 alignmentAgree the eval set, the current vendor's baseline number, and the acceptance thresholds before anything ramps. This is the meeting that de-risks the rest.

  2. Settle the deployment model in Phase 1Cloud vs. self-hosted and EU data residency shape security, cost and throughput — we decide it during the integration build, before the shadow-run leans on it, not at cutover.

  3. Lean on the shadow-run as the safety netIt's the direct answer to "what if it's worse than what we have today?" — run it on real traffic, discard the output, measure.

  4. Be explicit about what the numbers are and aren'tDisagreement vs. verdict, distributions vs. means. Setting that expectation early is what keeps the validation conversation honest all the way to cutover.
